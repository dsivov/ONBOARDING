How we run projects

A documentation-first, evidence-driven way of working — from the first idea to shipped, reviewed code. Every build traces to a written proposal; every claim traces to a measurement; every milestone is reviewed. This page explains the whole system and why each part exists.

Why a method

Structure you don't have to re-invent

Good projects fail for boring reasons: work starts before it's understood, claims ship unmeasured, reviews slip, and docs rot until nobody trusts them. This method removes those failure modes by making the good path the default path.

Write it down, prove it, review it — then the code almost plans itself.

Nothing here is heavy. It's a fixed set of artifacts, a handful of rules, and a consistent visual style — packaged so a new project inherits all of it on day one.

The artifacts

Ten documents, each with one job

ArtifactFormatAnswers

Plus DOCS_INDEX.md — the map of everything, ordered by pipeline stage. Every artifact has a fill-in template in templates/.

◆ RFC & DRP — approach and detail, agreed together
Don't treat these as a strict hand-off. The default is to co-author them — the RFC leads on approach (assemble/build/avoid, decisions), the DRP leads on detail (testable requirements, acceptance criteria) — and they cross-check as you go. Sequential (RFC→DRP) suits a contested approach you want signed off cheaply first; merged (one RFC with a requirements section) suits a small feature. The only invariant: approach + detailed requirements are agreed before the work plan.
A project, end to end

What actually happens

Understand

A BLOG frames the vision. An RFC turns it into a concrete proposal — what to reuse, what to build, the decisions and the phased plan. A DRP pins the detailed requirements and acceptance criteria.

Design

An ARCHITECTURE doc says how it's built — components, data model, boundaries. Later changes ride on CHANGE-REQUESTs that reference the architecture.

Plan

A WORK PLAN breaks it into phases and milestones. Every milestone has an explicit test gate written up front. Nothing is built that isn't a task here.

Build → review → advance

Each milestone: build on a feature branch, pass the gate, run a CODE REVIEW. Periodically, a CHECKPOINT takes the project's pulse. Repeat.

The rules that matter

The parts people skip (and shouldn't)

◆ R1 · Docs before code
No build without an RFC/DRP and a work-plan task. Discover work mid-build? Add the task first.
◆ R2 · Every claim is measured
Any performance/accuracy/"better-than" statement ships with a reproducible harness in scripts/ and the numbers in the doc. Can't measure it? Call it a hypothesis. An honest null result ("parity") beats an unverified win.
◆ R3 · Every milestone has a test gate
"The code exists" isn't done. The listed gate passing is done — and gates are written with the milestone, not after.
◆ R4 · Review before advancing
Code review at the end of each milestone. Critical/High get fixed (or logged as open findings) before the next milestone starts.
◆ R5 · Branches; never merge to main unverified
Work on feature/<name>. Merge only after the gate passes and review is clean. Commit/push when the human asks.
◆ R6 · Docs are honest & current
The final doc describes the destination, not the journey — cancelled ideas move to DECISIONS if they carry a lesson. When a measurement corrects a belief, fix the doc.
◆ R7 · Decisions logged, not re-litigated · R8 · Persist the non-obvious
Log every non-trivial choice in DECISIONS.md; keep project memory that isn't derivable from code or git.
◆ R9 · In planning, ask when unsure — with options
In the planning stages (discussion, RFC, DRP), don't guess at ambiguous scope, requirements, or approach — ask, and present suggested options (recommended first, each with its trade-off) so the person chooses fast. Resolve before finalizing the artifact; record the answer in DECISIONS.md. Ambiguity is cheapest to fix here.
◆ R10 · Design docs name the layout, the libraries, and what already exists
Every RFC / DRP / ARCHITECTURE / CR carries a code file-system layout (the tree, and what each path owns) and a external-libraries table (name, version, purpose, why over the alternative). Python? Ask which dependency manager — conda is the default; uv / poetry / pip+venv the alternatives. Existing codebase? Inventory the current layout, used libraries, databases and integrations first and reuse them — never add a second library that duplicates one already there. Replacing an incumbent means saying so, and planning its removal.
◆ R11 · The architecture contract is checked, not remembered
The moment the RFC + DRP are agreed, that agreement is frozen into docs/CONSTRAINTS.md — ~15 falsifiable sentences (A1…), plus non-goals, tripwires and an amendment log. Not a summary of the architecture: the parts that, if violated, mean we're building a different system than the one agreed. If a change would make one of those sentences false — stop. Report the drift (constraint ID · what the contract says · what the change needs · why) and offer comply / amend / defer. If the human approves the amendment, edit the contract first — version bump, amendment row, a D-NN in DECISIONS — then build. Never drift silently.

Why a contract, and when the agent reads it

A long build doesn't jump the rails; it drifts one reasonable-looking local decision at a time. Each step is defensible on its own, and thirty steps later the system is not the one that was approved. Reviews catch that late, when the drift is expensive. The contract catches it at the edit that causes it — but only if the agent actually consults it, and "check it when the decision is serious" is not a trigger anything can execute. So the trigger is three layers:

1 · Always resident

CLAUDE.md imports the contract (@docs/CONSTRAINTS.md), so it's in context from the first token of every session. This is why the file is hard-capped at one page and carries no diagrams or rationale — every line is paid for on every turn.

2 · Written checkpoints

The check is recorded, not merely thought: closing any RFC/DRP/ARCHITECTURE/CR, starting each milestone (a task in the plan), and a contract-check section in every code review and checkpoint — each constraint marked held / drifted / n/a.

3 · Tripwires

Named edits that force a re-read first: a new dependency, service or store · a new top-level directory or deployable · crossing a stated boundary · changing a public contract · introducing state, concurrency or caching · changing auth/tenancy/trust or the deployment target · anything on the non-goals list.

If the change would make a sentence in CONSTRAINTS.md false — stop, report, ask.

That last line is the whole mechanism. It turns "are we still aligned with the architecture?" — a judgment call that quietly degrades over a long session — into a text-consistency check against fifteen sentences. Which is exactly the kind of check that survives.

One more rule — and it's about who's in the room

◆ R12 · One human interface
The human talks to exactly one session: the manager. It owns every document, every review, and every call that needs a person. Any other session — a developer building against the plan — reports to the manager and waits. It never asks the human directly, and never invents an answer to keep moving. Four things force a report and nothing else does: a finished milestone, a blocker, a contract drift (R11), and work the plan doesn't have (R1/R10). Alone in a session? You're the manager, and R12 is already satisfied.

There are two different bottlenecks here and they want opposite treatment. Judgment is limited by human attention — it improves when every question arrives in one place, in order, to someone with the docs open. Typing is limited by permission prompts — it improves when nothing needs approving at all. One session can't be optimised for both; two can. That shape is the next section.

The GitHub cycle

How code reaches main

One branch per feature; commit per task; push per milestone; merge only when the gate passes and the review is clean. main stays releasable and green at all times.

Branch & commit

One branch per RFC/feature — feature/<name>, cut from an up-to-date main. Commit per task, each building, subject referencing the milestone. Fixes: fix/<name>; urgent: hotfix/<name>.

Push & PR

Push per milestone (and before a review). Open a draft PR early for visibility; the PR body links the RFC/DRP, the milestone, and the code review.

Merge gate

Merge to main only when all hold: test gate passes · code review clean (no open Critical/High) · CI green · PR approved. Prefer squash-merge; delete the branch.

Release

Tag vX.Y.Z when main reaches a shippable point. main is never broken, so any tag is releasable.

◆ Rule of thumb
Branch per feature · commit per task · push per milestone · merge per passed-gate-and-clean-review. Commit & push only when asked.
Two sessions

One session talks to you. The other never stops.

R12 says the human talks to one session. This is the shape that makes it pay off: two sessions, one repo, different jobs and deliberately different permission levels. A mode, not a requirement — small work stays single-session.

An agent that both writes the docs and types the code stops constantly: for permission, for a question, to show you something. Most of those stops don't need you — they need a decision from someone holding the plan. So separate them. One session holds the documents, the reviews and the human. The other holds nothing but the current milestone, and runs flat out inside a sandbox where nothing needs approving.

The four signals, and what comes back

SignalFires whenCarries
M<n> READYthe milestone's test gate passes (R3) branch + commit sha · the gate command and its result · one sentence on what changed. Requests the review (R4)
BLOCKEDit genuinely cannot proceed what's blocked · what was already tried · what it needs
DRIFT A<n>a change would make a constraint false (R11) constraint ID · what the contract says · what the change needs · why · comply / amend / defer
PLAN GAPthe work needs a task the plan doesn't have (R1), or a library not in the DRP's table (R10) what's missing · the task or dependency proposed · what it displaces
FINDINGS M<n>the manager finished the review the Critical/High IDs, the order to fix them in, the path to the CODE_REVIEW
PROCEED · ANSWER · AMENDEDcleared · decided · contract changed the next milestone · the decision (+ its D-NN) · the new contract version
◆ Having sent a signal, the developer stops
It does not start the next milestone. It does not find a smaller task to fill the wait. It does not "just tidy something up". The value of a checkpoint is that the code being reviewed isn't moving while it's reviewed — so waiting is the correct state, and a silent developer mid-milestone is the system working, not a session to go poke.

Why the servers belong to the manager

This one is mechanical rather than stylistic. The sandbox publishes no ports, so a server started inside it is unreachable from a browser — and we work remotely, so 127.0.0.1 is unreachable too. Long-lived servers therefore run on the host, started by the manager, always bound to 0.0.0.0. Short-lived test servers that live and die inside a test are the developer's business and stay there.

What the sandbox has to provide

Three requirements, and they exist so the messaging works at all — sessions advertise themselves in ~/.claude/sessions/<pid>.json, listen on a unix socket, and check each other's liveness against /proc/<pid>.

Same path, both sides

The repo mounted at the identical path in the sandbox and on the host — otherwise a pointer in a message doesn't resolve, and pointers are all the messages carry.

Shared ~/.claude

That's the session registry. Without it neither side can discover the other, so ListAgents comes back empty and there's nothing to address.

Shared PID ns + sockets

--pid=host and the cc-socks directory. Liveness is /proc/<pid>, so without a shared namespace each side prunes the other as a dead process.

◆ What the container actually buys you
A sandbox mounting your source and ~/.claude read-write, sharing the host PID namespace, reduces blast radius — it is not a security boundary. --dangerously-skip-permissions inside it is a bet that the agent won't wreck something git can't restore. It is not a bet that a hostile process can't get out. Worth knowing which bet you're making.

Running it

/new-project installs both launchers and both role briefs into .claude/roles/, inert until you use them. The launchers name the sessions (claude -n mgr-<project> / dev-<project>) and load the matching brief into the system prompt, so neither side has to discover anything:

◆ Two commands
.claude/roles/manager.sh — host, normal permissions, talks to you.
.claude/roles/developer.sh — starts the sandbox, then the developer inside it. --here skips the container; CLAUDE_DOCKER=<path> points at a different one.

Build → signal → wait → fix → build. You only ever see the manager's half of it.

And the degenerate case is the important one: a single session is the manager. It owns the docs, it talks to you, R12 holds trivially and this whole section is simply off. The artifacts, the gates and the reviews are identical either way — the split changes who does each part, never what gets done.

Skills that automate it

The method, one command at a time

Installable skills generate each artifact from the templates, so consistency is automatic:

◆ Authoring never asks permission
A bootstrapped project grants Read/Edit/Write on docs/** in .claude/settings.json, so the architect and manager skills write artifacts without a permission click. Scoped to docs/ deliberately — code changes still ask. The grant stays inactive until the workspace is trusted; the first interactive session's trust prompt switches it on.
Reuse before building

The skills delegate — they don't re-derive

R10 says one tool per job. That rule points at the method itself: where Claude Code already does something well, the house skill calls it and keeps only what's ours — the templates, the tokens, the severity scheme, the trace.

◆ Composition, not stage-switching
There is no per-stage enable hook — skillOverrides is static per project, and a project passes through every stage. So each SKILL.md names what to call and when, which is explicit and debuggable. The SessionStart banner already detects the stage from what exists in docs/ and prints the matching next step — no extra machinery needed.
◆ Deliberately not reused
The per-session task list, for work plans. Work-plan checkboxes are the durable cross-session trace; mirroring them would create two sources of truth that drift — the very thing R10 forbids.
Install, bootstrap, keep current

How the method reaches a project — and stays there

CommandWhenDoes
./install.shonceSymlinks the skills into ~/.claude/skills — updates propagate. --copy freezes them instead.
./new-project.sh <dir>day oneBootstraps a project unattended — --name (defaults to the directory name), --description, --dry-run.
./install.sh --new-project <dir>day oneBoth of the above in one command.
./sync-project.sh <dir>after a method changeRefreshes the copied templates, house.css and methodology; reports what needs a hand-merge.
◆ The unattended run is scoped, not a bypass
new-project.sh runs headless with --permission-mode acceptEdits plus the few shell commands the scaffold uses, so anything outside that set still stops. --yolo swaps in --dangerously-skip-permissions, which is not confined to the target directory. The script installs .claude/ itself, because writing hooks and settings is permission-gated in every mode short of a bypass — and it's a plain copy needing no judgment.
