    Solution / Software Architecturecanonical process

    From a one-line idea to a build plan someone else can execute

    A repeatable, documentation-first process for designing a solution: what you ask, what you decide, what you write down, and how each step is checked before the next one starts. Every stage below produces one durable artifact — and every artifact answers a question the next stage needs.

    What this deck is

    The process I follow, stage by stage, with a worked example carried end to end: an order & payments system.

    How to read it

    Present mode for walking through it. Reference mode for finding one thing fast while designing live.

    The claim

    Architecture is not the diagram. It is the set of decisions that are expensive to reverse — written down, justified, and checkable.

    ◆ Why artifacts, not meetings

    A meeting decides; a document is what the decision survives in. The test of this process is not that the documents exist — it is that later work is checkable against earlier work. A change request references the architecture section it touches. A test gate references the acceptance criterion it proves. A code review references the constraint it verified.

    Framewhat keeps the process honest

    Nine rules — these are the parts people skip

    The pipeline is the easy half. These are the disciplines that decide whether the documents stay true to the code six weeks in.

    1 · Docs before code

    No build starts without an agreed proposal and a plan task. Work discovered mid-build gets added to the plan first — a one-line task is fine.

    2 · Every claim is measured

    Any statement about latency, throughput, cost or "X beats Y" ships with a reproducible harness and the numbers. If you can't measure it, label it a hypothesis.

    3 · Every milestone has a test gate

    "Done" is not "the code exists". It is an explicit, pre-written set of assertions that pass. Gates are written with the milestone, never after.

    4 · Review before advancing

    End of each milestone: a review, findings triaged Critical / High / Medium / Security. Criticals and Highs are fixed before the next milestone opens.

    5 · Never merge unverified

    Branch per feature, commit per task, push per milestone, merge only on a passed gate and a clean review.

    6 · Docs describe the destination

    The final document says where we landed, not the detours. Cancelled ideas move to the decision log if they carry a lesson, and are deleted if they don't.

    7 · Decisions are logged, not re-litigated

    Every non-trivial choice gets an entry: context, options, choice, why. Re-opening a settled question requires a new entry, not a conversation.

    8 · In planning, ask — with options

    Never guess at ambiguous scope. Ask, and present options with their trade-offs, recommended one first. Ambiguity is cheapest to fix here and most expensive to fix in code.

    9 · The contract is checked, not remembered

    The agreed design is compressed to one page of falsifiable sentences. If a change would make one of them false — stop, report, decide. Drift never arrives as a side effect of a commit.

    ◆ The one rule to say out loud in an interview

    Rule 8. The most expensive architecture mistakes are requirement mistakes that were never surfaced as questions. Every stage below is really a device for making the unasked question visible while it's still cheap.

    Stage ①vision brief · html · 1–2 pages

    The Vision Brief: the problem, before anyone proposes a solution

    One short narrative that a non-engineer can read. It exists to stop the classic failure mode — a beautifully engineered answer to a question nobody asked. It is deliberately written before any technical proposal, so the proposal can be judged against it.

    What it answers

    The problem — what hurts today, for whom, and what it costs them. Concrete, with a real number if one exists.

    The idea — the shift, in one sentence a reader will remember.

    How it works — the mechanism, one diagram, no implementation detail.

    Why now — what changed that makes this possible or urgent.

    Where it goes — the arc, and what the proposal will cover.

    What it must not contain

    Technology choices. Component names. Database engines. Team allocations. Estimates.

    Every one of those is a decision that belongs to a later stage, where it can be justified against requirements that don't exist yet.

    If you cannot write the problem without naming the solution, you don't understand the problem yet — and that is the finding.

    The product frame — four facts the narrative won't pin down

    A story argues the case; it doesn't commit to anything. These four do, and nothing later in the pipeline carries them — the proposal and the requirements spec are both engineering-owned. This is the product tier, and it is a section rather than a stage.

    Segments

    Named and sized — not "users". "Tier-1 support, 240 agents, ~40 tickets/day each."

    Can't put a number on one? Say so. An unsized segment is an assumption.

    Jobs

    When … I want to … so that … — one line each, no solution named.

    The altitude between the story and F1…Fn: every requirement later traces up to one of these.

    Success metric

    One business number: baseline → target → by when, and how it's measured. Plus a guardrail that must not move.

    Business outcome, not latency — technical targets are NFRs.

    Launch criteria

    What must be true to roll out: migration verified, runbook written, pilot clean, rollback rehearsed, sign-off obtained.

    Not the milestone gates — those only prove the code is correct, not that it's safe to switch people onto.

    Worked example — the brief for our running system

    ◆ Vision Brief · Checkout & Order Capture

    Problem. Checkout is a single synchronous transaction that also calls the payment provider. When the provider is slow, checkout is slow; when it fails, we lose the basket. Last quarter, 2.1% of checkouts were abandoned on a payment timeout — roughly £180k of lost orders.

    Idea. Capture the order first and settle the payment second. The customer's commitment becomes durable at the moment they press pay, not at the moment a third party responds.

    How. Accept → persist the order in PENDING → authorise asynchronously → confirm. The customer gets an immediate acknowledgement and a confirmation moments later.

    Why now. The provider has just shipped webhook callbacks with signed payloads, which removes the need for us to poll.

    Where it goes. The proposal will cover order capture, payment orchestration and inventory reservation. It will not cover refunds, subscriptions or the catalogue.

    ◆ The product frame, for the same example

    Segments: returning shoppers on mobile (~68% of checkouts), guest checkout (~24%), partner marketplace orders (~8%). Jobs: "when I've decided to buy, I want my order confirmed immediately, so that I can leave the app and trust it happened." Metric: checkout abandonment on payment timeout — 2.1% → below 0.3% by end of Q3, from the funnel report; guardrail: chargeback rate stays under 0.4%. Launch criteria: 2-week pilot at 5% traffic with no Sev-1, reconciliation matches the provider's ledger for 14 consecutive days, rollback rehearsed, support runbook written.

    ◆ The sentence to steal

    "Last quarter, 2.1% of checkouts were abandoned on a payment timeout." — A vision brief with a number in it is a business case. Without one, it is an opinion. In an interview, if no number is offered, ask for it, and if none exists, state the one you're assuming.

    ◆ Where a PRD fits, if the organisation has one

    It is an upstream input, not a stage in this pipeline and never a co-author of the proposal. Its content lands in two places: segments, jobs, metric and launch criteria fill the product frame above; its detailed requirements become the numbered requirements in the spec. The PRD stays the authority for anything in the frame, so every fact keeps exactly one owner.

    Stage ①requirements gathering

    Seven buckets — ask in this order, every time

    Requirements gathering is not a conversation, it is a sweep. The order matters: each bucket narrows the space the next one searches. Scope before scale; scale before consistency; consistency before technology.

    Ask with options

    Not "what's your availability target?" but "three nines, or four? Four roughly triples the infrastructure and puts someone on call — worth it?"

    Write the answers where both can see

    Numbers go on the board immediately. They become the acceptance criteria, and later the test gates.

    Record the unknowns

    An unanswered question is an assumption. Name it, state which way you're designing, and note what would change if the answer flips.

    ◆ In the worked example

    Actors: shopper (web + mobile), warehouse system, finance reconciliation, customer support. Success: "a customer who pressed pay always ends up with either an order or their money, never neither and never both." Non-goals for v1: refunds, partial shipment, subscriptions, multi-currency settlement. Fixed: the date — Black Friday.

    Stage ①question bank · 2 of 4

    Scale, latency and availability — get numbers, not adjectives

    "Fast", "real-time", "highly available" and "a lot of users" are not requirements. Convert each of them into a number and a percentile before you accept it.

    AskWhyWhat the answer changes
    How many users, and how many of them are active in the busiest hour?Peak drives capacity, not averageInstance count, connection-pool sizing, and whether you need queue-based load levelling at all
    What's the read-to-write ratio?Reads and writes scale by different meansHigh read ratio ⇒ cache + read replicas + possibly a separate read model (CQRS). Write-heavy ⇒ partitioning and batch/async writes
    What is the traffic shape — steady, diurnal, or spiky?A 20× flash sale is a different system from a 2× daily peakSpiky ⇒ a queue in front of the write path, admission control, and autoscaling that can't react fast enough (so pre-scale)
    "Fast" at which percentile — p50, p95 or p99?p99 is where architecture livesA p99 budget forces you to count the network hops on the hot path. Each synchronous call to a dependency spends part of that budget
    Is the latency budget end-to-end or per service?Budgets must be allocated, not repeatedTurns into a per-hop allocation table — and usually reveals that one external call cannot fit, which forces async
    What availability target, and measured how?99.9% vs 99.99% is a 10× cost stepThree nines ⇒ single region, rolling deploys, business-hours on-call. Four nines ⇒ multi-AZ, automated failover, redundant everything, 24/7 rota
    What does the system do when it's degraded — refuse, queue, or serve stale?Degradation is a product decisionDetermines whether you build a fallback path, a queue, or a maintenance page. Nobody thanks you for choosing this at 3 a.m.
    What does 10× look like, and when?Distinguishes today's design from tomorrow'sLets you name what you're deliberately not building yet, and what the migration would be — a strong answer, not a weak one
    ◆ The trap

    "It must be real-time." Ask: real-time for whom, and what breaks at one second? Most "real-time" requirements are sub-minute freshness requirements, and the difference between them is an event stream versus a cron job — an order-of-magnitude difference in cost and complexity.

    Stage ①question bank · 3 of 4

    Data, consistency and the rules you don't get to negotiate

    This bucket produces the constraints that are hardest to retrofit. A consistency requirement discovered in month four is a rewrite; a compliance requirement discovered in month four is a rewrite and a conversation with legal.

    AskWhyWhat the answer changes
    For each entity — who is the source of truth?Two owners means eventual corruptionDraws the service boundaries. If two services can both write an entity, they are one service with a bug
    Which operations must be atomic, and which may be eventually consistent?The single most consequential answerAtomic ⇒ one transaction, one database, one service. Eventual ⇒ saga + compensations + outbox, and a visible intermediate state in the UI
    If eventual — how eventual? Seconds, minutes, or "before the customer notices"?Bounds the staleness budgetDetermines polling interval vs push, and whether the read model can be rebuilt lazily or must be kept hot
    Can the same request arrive twice?It can. It always canForces idempotency keys, a uniqueness constraint, and a decision about what "the same request" means
    RPO and RTO — how much data may we lose, and for how long may we be down?Backup strategy is derived, not chosenRPO 0 ⇒ synchronous replication. RPO 15 min ⇒ PITR with WAL shipping. RTO 5 min ⇒ warm standby and a rehearsed failover
    What's the retention policy, and is there a right-to-erasure obligation?Deletion is a schema decisionErasure ⇒ no PII in immutable event logs, or crypto-shredding. Also drives partitioning by time and an archival path
    Do we need history — audit trail, point-in-time reconstruction, or just "who changed it last"?Three very different designsupdated_by column vs an append-only audit table vs event sourcing. Pick the cheapest one that satisfies the actual obligation
    Which fields are regulated — card data, health, personal identifiers? Any residency rules?Scope of the compliance boundaryPCI ⇒ never store the PAN; tokenize at the edge and keep the provider's token. Residency ⇒ region-pinned storage, which constrains the whole topology
    ◆ In the worked example

    Atomic: order + order lines + outbox row, one transaction. Eventual: inventory reservation and payment authorisation, budget ~10 s, visible to the customer as "confirming your order". Idempotency: a client-generated key per checkout attempt, unique per customer. PCI: the card never touches our servers — the provider's hosted field returns a token. RPO 0 / RTO 5 min for orders; the read model may be rebuilt.

    Stage ①question bank · 4 of 4

    Integrations and the constraints of the world you're deploying into

    This is where a design meets the organisation. Most architectures are not limited by what is technically possible but by what the surrounding systems, the platform team and the budget allow.

    AskWhyWhat the answer changes

    ◆ The question that most impresses

    "What happens today when the payment provider is down for twenty minutes?" It is a requirements question, an integration question and a product question at once — and the answer almost always reveals a behaviour nobody had written down.

    Stage ①estimation

    Do the arithmetic out loud — it decides the architecture

    Four calculations, five minutes, and they eliminate most of the design space before you draw a single box. Do them on the board so the interviewer can follow — and so the numbers are there to be pointed at when you justify a choice later.

    ① Throughput
    # orders per day → writes per second
1,000,000 / 86,400  ≈ 12 writes/s average
peak = 20× (flash sale) ≈ 240 writes/s
read:write = 100:1      ≈ 24,000 reads/s peak

    Consequence: 240 writes/s is comfortable for a single relational primary. The reads are not — they need a cache and read replicas. No sharding is justified at this scale, and saying so is a stronger answer than sharding pre-emptively.

    ② Storage
    # row size × volume × retention
order 1 KB + 3 items × 300 B ≈ 2 KB
2 KB × 1M/day  = 2 GB/day
              → ~0.7 TB/year
7-year retention ≈ 5 TB

    Consequence: fits one managed Postgres with monthly partitioning; partitions older than 18 months move to cold object storage. Retention is a schema decision, taken now.

    ③ The latency budget
    # p99 checkout budget: 800 ms
edge + auth        40 ms
order service      30 ms
db write (tx)      20 ms
inventory (sync?) 120 ms
payment PSP p99   1200 ms  ← does not fit
                  ─────────
sync total       1410 ms ✗

    Consequence: the arithmetic — not taste — forces payment off the synchronous path. This single calculation justifies the entire asynchronous design.

    ④ Cost of the shape
    # rough monthly order of magnitude
app tier   6 × 2 vCPU     ~$400
postgres   1 primary+2 RR ~$900
cache      1 small pair   ~$150
broker     3 brokers      ~$600
                          ──────
                          ~$2,050/mo

    Consequence: the broker is a third of the bill. Worth asking whether a database-backed outbox poller would do for v1 — and worth saying you asked.

    ◆ Numbers to have memorised

    86,400 s/day · 2.6M s/month · 1M/day ≈ 12/s · peak is 2–10× average (20×+ for flash events) · a single Postgres primary handles thousands of simple writes/s · one app instance serves a few hundred RPS when it touches a database. Full cheat-sheet at the end of this deck.

    Stage ①rule 8 in practice

    When the answer isn't available — assume loudly

    You will not get every answer. The professional move is never to guess silently; it is to state the assumption, design against it, and name the signal that would change your mind.

    The three-part move

    1 · Name the assumption. "I'm going to assume orders are single-currency."

    2 · Design against it. Proceed — don't stall the design on an open question.

    3 · Name the blast radius. "If that's wrong, it changes the schema — an amount column becomes amount plus currency plus a rate at capture time — but it doesn't change the topology."

    The third part is what separates an architect from a developer: you are quantifying the cost of being wrong, not just admitting you might be.

    Offer options, recommended first
    // how to put a question
Q: Should inventory be reserved
   synchronously at checkout?

A) Reserve async, oversell risk  ← recommended
   cheap, fast checkout, needs a
   compensation path
B) Reserve sync, no oversell
   +120 ms on p99, couples checkout
   to the inventory service
C) Reserve sync only for low stock
   hybrid; more code, best of both

    Three options, a recommendation, and the cost of each. A stakeholder can answer that in ten seconds; they cannot answer "what do you want?" at all.

    The traps, and the question that defuses each

    What you hearWhat it usually hidesDefuse it with
    "It must never lose data."An unpriced RPO of zero, which means synchronous replication and a real cost"Never lose a committed order, or never lose an in-flight request? The second one costs about 3× the first."
    "It should be real-time."Sub-minute freshness, not sub-second"What breaks if it's one second late? One minute?"
    "We need it to scale."No number, and often no growth model"To what, by when? I'd rather build for 10× and name the migration to 100×."
    "Use microservices."A solution presented as a requirement"What are we trying to gain — independent deploys, team autonomy, or isolation of one hot path? Each points at a different split."
    "It's just a small change."A public contract change"Does anything outside this service depend on that shape? If yes, it's an additive change plus a deprecation window."
    "The old system does X, keep that."A behaviour nobody can justify but everyone depends on"Who consumes X today? If we can't find a consumer, that's a non-goal worth writing down."
    Stage ①the hardest separation to make

    Is it a requirement, or a solution wearing a requirement's clothes?

    "We need an MCP server" sounds like a solution — until the consumer turns out to be an AI agent, and then it sounds like a requirement. The ambiguity is real, not a lapse in your thinking: protocol choices sit exactly on the boundary, and there is a named frame for why.

    The reframe — three buckets, not two

    BucketThe testOwned byWhere it lives
    NeedThey would reject the system if it were unmet — and they can state it without naming a technologyThe stakeholderRequirements: F1…Fn and NFR-*
    ConstraintA decision already made outside your project that you must design aroundSomeone else — name them, and date itConstraints & assumptions, with its source and whether it's negotiable
    ChoiceYou are free to decide, and a substitution would go unnoticed outside the boundaryYouA decision record: what was chosen, against what, and what would reverse it

    Most of the difficulty comes from forcing a binary. "We need MCP" is almost never a need — it is usually a constraint, and constraints belong in the requirements document labelled as constraints. That label is the whole trick: you still honour the statement, but you keep the information that it was inherited rather than derived.

    Four tests that sort a statement in seconds

    1 · The why / how ladder

    Ask why to climb toward needs, how to descend toward solutions. Stop climbing when the stakeholder stops caring — that rung is the requirement for this engagement.

    "we need MCP"
 ↑ why?  so Claude can call our tooling
 ↑ why?  so agents resolve tickets in-chat
 ↑ why?  cut handle time 30%  ← the need
    2 · The substitution test

    "If I delivered Y instead of X, everything else equal, would you reject it?"

    Offer REST + OpenAPI with a thin function-calling shim instead of MCP. A shrug means it was a choice. "Our runtime only speaks MCP and we can't change it" means constraint — and you have just learned the domain assumption D that pins the design.

    3 · The fit-criterion test

    Every requirement needs a measurable criterion that isn't circular. "The system exposes MCP" is testable, but it only tests itself.

    Rewrite as a capability: "an autonomous agent can discover the available operations and invoke them at runtime without bespoke integration code." Now MCP passes — and so does OpenAPI plus function calling.

    If only one implementation could ever pass your criterion, you wrote a solution. This is the sharpest single test of the four.

    4 · The owner test

    "Who can change this, and what would it cost them?"

    Nobody here ⇒ constraint. Us, within a sprint ⇒ choice. The customer owns exactly one of the three buckets, and it is the first one.

    This is also the question that surfaces a constraint nobody wrote down — which is usually the most valuable thing you extract in the first ten minutes.

    The example, worked

    Support agents resolve tickets in-chat; handle time −30%needA business outcome — it survives any technology change

    ◆ What falls out of sorting it

    Two consumers with different interaction models is a need; two protocols is a consequence. That framing hands you the design — one core, two adapters — and makes the trade-off statable: "if the runtime constraint lifts, the MCP adapter is deletable without touching the domain."

    ◆ What to say in the room

    Don't silently reclassify — narrate it, then convert it into a question:

    "I'd note MCP as a constraint rather than a requirement, and record who owns it — because if it's negotiable the design space opens up. So: is MCP fixed by your agent platform, or is it your team's proposal? … Fixed. Then the requirement underneath is 'an autonomous agent can discover and invoke operations without bespoke integration code', MCP is how we satisfy it for this consumer, and I'll keep it behind an adapter so it stays replaceable."

    Three things land at once: you know the distinction, you don't waste time re-litigating a decision that is already made, and you have protected the design from a constraint you don't control.

    When a statement names a technology, don't accept it and don't reject it — climb one rung, restate the capability underneath, and ask who owns the choice.

    Stage ②Stage ③proposal + requirements

    The proposal and the requirements are written together

    These two are a coupled pair, not a hand-off. Approach and detail are entangled: a requirement no approach satisfies cheaply means the approach is wrong; an approach that silently drops a requirement means the requirements are wrong. Writing them in sequence hides both.

    The RFC's three columns

    Assemble — what already exists that we reuse. Listing this first is the strongest anti-over-engineering device there is.

    Build — the genuinely new parts. If this column is long, challenge it.

    Avoid — explicit non-goals, with the reason.

    The DRP's job

    Turn each line of the proposal into something a test can check. Requirements get IDs; every acceptance criterion later becomes a milestone gate.

    The exit condition

    Both agreed ⇒ compress into the contract. That is the first moment a top-level design exists to hold anyone to.

    ◆ The detailed requirements doc is not a PRD

    Worth being precise about, because it's the first thing an interviewer from a product-led org will query. The stage-3 document here is the engineering requirements spec — an SRS for the requirements half plus design detail for the rest: layout, pinned libraries, integrations with their failure policies, cross-cutting concerns. Engineering owns it, and its authors are the same people who write the proposal — which is exactly what makes co-authoring the two correct.

    A PRD sits at a different altitude — problem, personas, user stories, success metrics, release criteria — and if the organisation has one it is an upstream input, never a co-author: product decides what and why, this pair decides how. Say that and you defuse the obvious objection, which is "why would a PM co-author an engineering proposal?" They wouldn't.

    An NFR without a measurement method is a wish. With one, it becomes a test gate — and the milestone that claims to satisfy it cannot close until that harness runs and passes.

    Stage ③traceability

    Requirement → acceptance criterion → test gate → review

    This chain is the whole reason the process is worth its overhead. Each link cites the previous one by ID, so at any point you can ask "which requirement does this test protect?" and "which test proves this requirement?" — and get an answer without a meeting.

    Writing an acceptance criterion that a test can execute

    Not this

    "Orders should be handled reliably."

    "The system performs well under load."

    "Payments are secure."

    None of these can fail. A criterion that cannot fail is not a criterion.

    This

    F3 — submitting the same basket twice with idempotency key K returns HTTP 200 with the identical order_id both times, and exactly one row exists in orders.

    NFR-latency — at 240 writes/s sustained for 10 minutes, p99 of POST /orders is ≤ 800 ms, measured by scripts/bench_checkout/.

    F4 — when the provider returns declined, within 10 s the order is CANCELLED and the reservation row is released.

    ◆ The rule this enforces

    Rule 3 — every milestone has a test gate, written with the milestone. Rule 2 — every claim is measured. An NFR with a number and no harness is the single most common place both rules are quietly skipped.

    Dependency analysis — four kinds, and each fails differently

    Stage ②assemble · build · avoid

    Name the alternatives, then say what you're choosing against

    A design with no rejected alternatives has not been designed — it has been assumed. The trade-off table is the single most useful thing in an architecture document, and the thing an interviewer is most reliably listening for.

    Assemble — reuse

    Managed Postgres · the org's OIDC provider · the shared observability stack · Terraform modules · the existing inventory service

    "I'm choosing A over B. The cost of that is C. The signal that would make me switch is D." — The fourth clause is what turns a preference into an engineering position, and almost nobody says it.

    Stage ②decisions.md · the running log

    Every non-trivial choice gets four lines and an ID

    The decision log is not documentation of the design — the architecture document does that. It is documentation of the reasoning, which the architecture deliberately discards. Its job is to stop settled questions from being re-opened in month three by someone who wasn't in the room.

    The format
    ## D-007 — Payment leaves the synchronous path
Date:    2026-03-11
Status:  accepted
Context: p99 budget is 800 ms; the provider's
         own published p99 is 1.2 s.
Options: (a) sync authorise — breaks budget
         (b) async + 202 — chosen
         (c) sync with 400 ms timeout + fallback
             — unacceptable decline rate

         our own availability calculation.

    What earns an entry

    Anything you would have to defend, anything expensive to reverse, and anything you rejected for a non-obvious reason.

    Also: every reversal. A decision that changes gets a new entry that supersedes the old one — the old one stays, marked superseded. The log is append-only.

    What doesn't

    Naming conventions, formatting, library minor versions, anything the code makes obvious. A log full of trivia is a log nobody reads.

    The interview version

    You won't write these live — but saying "I'd record that as a decision, because in six months someone will ask why we didn't just call the provider synchronously" demonstrates the instinct, which is the point.

    ◆ The failure this prevents

    Six weeks in, a new engineer sees an async payment flow, thinks "this is needlessly complicated", and proposes simplifying it. Without D-007 that costs a week of argument. With it, it costs thirty seconds — and if they have new information, they write D-019 and supersede it, which is exactly what should happen.

    ◆ The drift protocol

    If a change would make a sentence here false — stop. Do not implement it and mention it afterwards. Report: the constraint ID, what the contract says, what the change needs, why, and three options — comply (fit the contract), amend (change the contract), defer (park it as an open finding). On approval: amend the contract first, bump the version, add an amendment row, log the decision, then build. Contract changes never arrive as a side effect of a commit.

    Note what this is: a text-consistency check, not a judgement call. That is precisely why it survives a long project.

    Stage ④architecture · html · the design of record

    Seven sections, and the zoom level each one works at

    The architecture document is written once per system; every change after it is a scoped change request that cites the section it touches. Its sections map cleanly onto the C4 zoom levels, which is a convenient thing to be able to say out loud.

    ◆ Two sections that are mandatory and usually missing

    Section 5 — the file-system layout and the pinned library table. A reader must be able to place a new file without asking anyone, and no dependency gets added mid-build that isn't listed here. Section 6 — boundaries. Most "architecture" documents describe components and never say who is allowed to write to what, which is where the coupling actually lives.

    Stage ④component decomposition

    Cut along capabilities and data ownership — never along technical layers

    The classic mistake is to split a system into "the API layer, the business layer, the data layer" and call those components. Those are layers inside a component. Components are cut where the data ownership changes, because that is the only boundary that is expensive to move later.

    Start coarse, split on evidence

    A modular monolith with clean internal boundaries can be split later. A distributed system with the wrong boundaries cannot be merged later — you'd be undoing a network protocol.

    So: start with the fewest deployables that satisfy the failure-isolation and scaling requirements, and keep the module boundaries strict enough that a split is a refactor rather than a rewrite.

    The questions that justify a split

    Does it need to scale independently — with a number?

    Does it need to fail independently?

    Does it need to be deployed independently by a different team?

    Does it have a different data owner or compliance boundary?

    No to all four ⇒ it is a module, not a service.

    Stage ④integrations · inbound

    Inbound: the contract you can't take back

    An exposed contract is the most expensive thing in the system to change, because you don't control who depends on it. Decide the style, the versioning policy and the idempotency semantics before the first consumer integrates — after that, they're permanent.

    Choosing the style
    StyleReach for it when
    REST/JSONPublic or partner-facing; cacheable reads; the default until something forces otherwise
    gRPCInternal, chatty, latency-sensitive; you control both ends and want a generated contract
    GraphQLMany clients with divergent read shapes; you accept the caching and N+1 cost
    Webhook outThe consumer wants push and can host an endpoint
    Batch / fileThe other side is a legacy or finance system; volume is high and freshness isn't needed
    The inbound checklist

    Contract-first — OpenAPI or protobuf in the repo, generated clients, contract tests in CI.

    Versioning — /v1 in the path, additive-only changes, a stated deprecation window.

    AuthN / AuthZ — OIDC bearer for users, mTLS or signed HMAC for partners; authorise per resource, not per route.

    Idempotency — an Idempotency-Key header on every unsafe method, stored and enforced by a unique index.

    Pagination — cursor, not offset; offset pagination breaks under concurrent writes.

    Rate limits — per client, with 429 plus Retry-After, and documented.

    Errors — one shape, machine-readable code plus human message; never leak internals.

    Payload caps — a maximum body size and a maximum collection length, enforced at the edge.

    // POST /v1/orders — the contract, written before the code
Headers  Authorization: Bearer <oidc>
         Idempotency-Key: 018f3c2a-...   // client-generated, unique per attempt
Body     { "basket_id": "...", "items": [{ "sku": "...", "qty": 2 }],
           "currency": "GBP", "total_minor": 4599 }

202      { "order_id": "018f...", "status": "PENDING",
           "poll": "/v1/orders/018f.../status" }   // not 201 — settlement is async
200      // same Idempotency-Key replayed → the original response, unchanged
409      { "code": "IDEMPOTENCY_KEY_REUSED", ... }  // same key, different body
422      { "code": "BASKET_EXPIRED", "message": "...", "field": "basket_id" }
429      Retry-After: 2
    ◆ The detail that signals experience

    Returning 202 rather than 201, and defining what happens when the same key arrives with a different body. Most designs define the happy replay and forget the conflicting one — which is the case that actually corrupts data.

    Stage ④integrations · outbound

    Outbound: every call is a dependency on someone else's bad day

    For each outbound dependency, write one row: timeout, retry policy, breaker threshold, fallback, and where the request ends up if all of that fails. A design that doesn't have this table has silently chosen "hang forever, then cascade".

    DependencyTimeoutRetryBreakerFallback / terminal state
    Payment provider800 ms3× exp+jitter50% of 20Order stays PENDING; retried by the poller; after 30 min → CANCELLED + customer notified
    Inventory reserve300 ms2× exp+jitter50% of 20Reserve optimistically, compensate on later failure — an accepted, bounded oversell risk

    ◆ Two rules that prevent most cascade failures

    Never retry a non-idempotent call without an idempotency key — you will double-charge someone. Never let a timeout exceed the caller's own deadline — a 30 s timeout inside an 800 ms budget is not a timeout, it is a queue of doomed threads.

    Stage ④integrations · asynchronous

    The outbox: how a database write and a message become one atomic act

    The dual-write problem is the defining correctness bug of event-driven systems: commit the row, then publish the event, then crash — and the rest of the world never learns. The fix is to make the event part of the same transaction as the row.

    Events vs commands

    Event — a fact that happened: order.confirmed. Past tense, no addressee, many consumers, the publisher doesn't care who listens.

    Command — a request for something to happen: authorise_payment. Imperative, exactly one handler, the sender expects an outcome.

    Mixing them is how you end up with a message bus that is secretly a synchronous RPC with worse error handling.

    The four things to decide per topic

    Partition key — order_id. Ordering is guaranteed per partition only, so the key is the ordering guarantee.

    Schema & evolution — a registry, backward-compatible changes only; consumers must tolerate unknown fields.

    Retention & replay — 7 days here; long enough to rebuild a consumer after an incident.

    Failure path — retry topic, then DLQ, with an alert. A message that can never be processed must not block the partition behind it.

    Stage ④key flows · happy path + the two that fail

    The main flow, and what happens when each step doesn't

    Document three flows, never one: the happy path, the most likely failure, and the nastiest failure. The third is where the design is actually tested — in our case, the payment succeeding while our own confirmation write fails.

    ◆ The invariant this protects

    Back to the success sentence: "a customer who pressed pay always ends up with either an order or their money, never neither and never both." Every box above exists to keep that one sentence true. Trace each component back to the invariant it protects — that is the difference between a design and a diagram.

    Stage ④data · the choice before the schema

    Pick the store from the access pattern, not the trend

    Default to one relational database and make anything else earn its place. Every additional store is a second backup story, a second failover story, a second consistency model and a second thing to be woken up for.

    ◆ The polyglot-persistence trap

    Choosing five stores because each is individually optimal produces a system whose operational burden is the sum of five, and whose consistency model is the product. Constraint A3 exists precisely to make adding a second durable store a decision someone has to defend.

    Stage ④data · the schema

    Schema: entities, keys, indexes, and the constraints that enforce the invariant

    A schema is not a list of tables — it is where the business invariants are enforced. Anything the database can guarantee, the database should guarantee, because application code is optional and constraints are not.

    create type order_status as enum
  ('PENDING','AUTHORISED','CONFIRMED','FULFILLED','CANCELLED');

create table orders (
  id            uuid        primary key,              -- v7: time-ordered, index-friendly
  customer_id   uuid        not null,
  status        order_status not null default 'PENDING',
  currency      char(3)     not null,
  total_minor   bigint      not null check (total_minor >= 0),  -- A7: never float
  version       int         not null default 0,          -- optimistic locking
  created_at    timestamptz not null default now(),     -- always tz-aware
  updated_at    timestamptz not null default now()
) partition by range (created_at);                 -- monthly; drives archival

-- one payment per order, enforced by the database, not by hope
create unique index payments_one_per_order on payments (order_id);
-- replay protection: the same key from the same customer is the same order
create unique index idem_unique on idempotency_keys (customer_id, key);
-- support lookups (F6) — three access paths, three indexes, decided now
create index orders_by_customer on orders (customer_id, created_at desc);
-- the poller only ever reads unpublished rows: a partial index keeps it O(pending)
create index outbox_pending on outbox (id) where published_at is null;
    Migrations

    Versioned, forward-only, one tool (Flyway / Alembic / Prisma Migrate). Expand-then-contract for every breaking change: add the new column, backfill, switch reads, drop the old one — four deploys, zero downtime.

    Indexes are a design decision

    Every index is a write cost paid on every insert. Derive them from the listed access paths, not from a slow-query log six months later.

    What the DB must enforce

    Uniqueness, foreign keys, check constraints, not-null. If the only thing stopping two payments for one order is application code, there will eventually be two payments for one order.

    The directory tree, written before the code exists

    The test is simple and unforgiving: a reader must be able to place a new file without asking anyone. A layout that fails that test will be reorganised three times during the build, and each reorganisation is a day of review noise.

    The rule this tree encodes

    Dependencies point inward only: adapters → ports → core. The core imports nothing from adapters — that is constraint A2, and it is checkable by a lint rule rather than by reviewer diligence.

    The payoff is testability: the entire domain is unit-testable with no database, no broker and no Spring context, which is why the unit suite runs in seconds and gets run.

    Mark what exists vs what's new

    On a brownfield project the tree must show both — [new] and [exists].

    It forces the inventory question: what is already here, which libraries are actually imported, which databases and integrations are live? Build on them. Introducing a second HTTP client or a second ORM alongside an incumbent is the failure this section exists to prevent.

    If you genuinely must replace an incumbent: say so, justify it, and put its deletion in the same work plan. A half-migration that leaves both is worse than either.

    Stage ④the checklist that gets skipped

    Cross-cutting concerns — decided once, applied everywhere

    These do not belong to any single component, which is exactly why they get forgotten until an audit or an incident. Walk this list before you call a design finished; it takes ninety seconds and it is where the follow-up questions come from.

    Identity & access

    AuthN at the edge (OIDC); the gateway validates and forwards a signed identity — no service trusts another's claims.

    AuthZ per resource, not per route. Ownership checks live in the domain, not the controller.

    Service-to-service: mTLS or short-lived tokens. Never a shared static secret.

    Secrets & config

    Secrets in a managed store, injected at runtime, rotated on a schedule. Never in the image, never in the repo, never in an environment variable that gets logged.

    Config is per-environment and validated at startup — fail fast on a missing value rather than at the first request that needs it.

    Observability

    Logs structured, with a correlation id propagated through HTTP and the broker.

    Metrics RED per endpoint (rate, errors, duration) and USE per resource; queue depth and outbox lag are the two that predict incidents here.

    Traces on the whole hot path, sampled.

    SLOs with an error budget — the number that decides whether to ship or stabilise.

    Privacy & data protection

    Classify every field: public / internal / personal / regulated. The classification drives encryption, logging rules and retention.

    PII never enters an immutable event log unencrypted — right-to-erasure and immutability are in direct conflict, and crypto-shredding is how you resolve it.

    Card data is tokenised at the edge; our PCI scope stays at SAQ-A.

    Failure & safety

    Every external call: timeout, retry policy, breaker, fallback. No exceptions.

    Every consumer: idempotent, with a DLQ someone watches.

    Graceful degradation is designed, not improvised: what still works when the provider is down?

    Change & operability

    Feature flags for anything risky; expand-then-contract for every schema change.

    Zero-downtime deploys, and a rollback that is rehearsed rather than theoretical.

    Runbooks for the three most likely alerts, written by whoever built the thing.

    A cost model per environment, tagged, and reviewed monthly.

    ◆ The one people forget

    Rollback of a schema change. Code rolls back in seconds; a migration that dropped a column does not. This is why every breaking change is expand-then-contract — and why the contract-and-drop step is a separate deploy, days later, once the rollback window has closed.

    Stage ④where it actually runs

    Topology, the pipeline that gets code there, and what breaks first

    A design that stops at the component diagram is half a design. The deployment topology determines your real availability number, and the failure table is the part an experienced interviewer will push hardest on.

    Environments & pipeline

    dev — ephemeral, per pull request, seeded data. staging — production-shaped, real integrations in sandbox mode. prod — the only one with real keys.

    Pipeline: build → unit → integration (Testcontainers) → contract tests → deploy staging → smoke → canary 5% → full. Infrastructure is Terraform, reviewed in the same pull request as the code that needs it.

    What breaks first, in order

    1 · The payment provider. Highest-latency, least-controlled dependency. Contained by the async design and the breaker.

    2 · The database connection pool. The real ceiling long before CPU is. Contained by pool sizing derived from the throughput math and a hard statement timeout.

    3 · Outbox lag. If the publisher can't keep up, confirmations slow and the NFR breaks silently — which is why lag is an alert, not a dashboard.

    4 · A hot partition. Keying by order_id avoids it; keying by customer_id would not.

    Stage ⑤work plan · phases → milestones → tasks

    Sequence the build so the riskiest thing is proven first

    The plan turns the requirements and the design into phases, each ending at a milestone with an explicit test gate. The sequencing principle is not "build the easy parts first" — it is build the thin vertical slice that proves the risky assumption, then widen it.

    Sequencing rules

    Risk first. The assumption that would invalidate the design gets tested in P1, not P4.

    Vertical, not horizontal. Never "all the controllers" then "all the repositories" — that defers integration risk to the end, which is where it does the most damage.

    Every phase opens with a contract check. Which constraints does this phase touch, and do they still hold?

    Nothing gets built that isn't a task here. Work discovered mid-build is added to the plan first — even as a one-liner.

    The checkboxes are the status report. There is no separate one.

    Stage ⑥Stage ⑦the loop that keeps design and code in step

    Review each milestone, check the contract, and let the trace be the status

    The review is not a formality at the end — it is the mechanism that keeps the built system and the designed system the same system. Its most valuable section is the one nobody expects: the contract check.

    The milestone review

    Findings by severity — Critical / High / Medium / Security, each with a file, a line and a concrete failure scenario. No Critical or High may be open when the next milestone starts.

    The gate result — the exact command and its output, pasted. "Tests pass" is not evidence; 34 passed in 8.2s is.

    The contract check — every constraint marked held, drifted or n/a. A drift stops the build and goes to a human with three options: comply, amend, defer.

    The progress trace — five artifacts, no status meeting

    1 · Work-plan checkboxes.
    2 · One code review per milestone, dated.
    3 · Periodic checkpoint reviews, with prior findings marked ✅ fixed or carried with a reason.
    4 · The decision log, for course changes.
    5 · Git history on the feature branch.

    Anyone can reconstruct where the project is from those five. That is the actual deliverable of the process — not the documents, the reconstructability.

    The merge gate — a branch reaches main only when all four hold

    1 · Gate passes

    The milestone's listed assertions, green.

    2 · Review clean

    No open Critical or High.

    3 · CI green

    Including the contract tests.

    4 · Approved

    By a human who read the diff.

    Branch per feature · commit per task · push per milestone · merge per passed-gate-and-clean-review.

    ◆ Where this differs from most processes

    Most review checklists ask "is this code good?". This one also asks "is this still the system we agreed to build?" — and that second question is the one that catches architectural drift, because drift never looks wrong locally. Each individual decision is reasonable. The sum is a different system.

    Deliveryhow the process runs with AI-assisted implementation

    One interface for judgement, one for throughput

    A modern twist worth being able to talk about: when implementation is agent-assisted, the bottleneck moves. Judgement is limited by human attention; typing is limited by interruptions. Those want opposite treatment, so we split them.

    Manager — owns the documents and the human

    Holds every artifact in docs/. Plans, reviews each milestone, amends the contract, logs decisions, runs the servers, answers questions.

    It is the only interface a person talks to — so every question arrives in one place, in order, to someone with the design open.

    Developer — owns the code and nothing else

    Holds only the current milestone. Implements plan tasks, writes tests, runs the gate, commits. Runs in a sandbox where nothing needs approving, so it never stops for permission.

    The asymmetry is the design: more machine permission, less authority. It can do anything to the sandbox and nothing to the plan.

    Signal (developer → manager)Fires whenManager's reply
    M<n> READYThe milestone's test gate passes — carries branch, sha and gate outputFINDINGS M<n> with the ordered Critical/High list, or PROCEED
    BLOCKEDIt genuinely cannot proceed — what's blocked, what was triedANSWER, with a decision-log id if it was worth recording

    Four signals, and nothing else stops the build. Having sent one, it waits — because the value of a checkpoint is that the code being reviewed isn't moving while it is reviewed. A single session is simply the manager, and nothing else about the process changes.

    Sentences worth having ready

    Framing an assumption
    "I'm going to assume single-currency. If that's wrong it changes the schema but not the topology."

    Pricing a choice
    "I'm choosing A over B. It costs C. The signal that would make me switch is D."

    Refusing a premature answer
    "That's a requirements question rather than a design one — can I ask what the acceptable staleness is before I choose?"

    Letting the numbers decide
    "The number that settles this is the provider's p99. Below 300 ms I'd keep it synchronous; at 1.2 s it has to come off the hot path."

    Not knowing something
    "I don't know that figure. Here's how I'd measure it, and here's a design that's robust to either answer."

    Declining scope
    "That's a non-goal for v1 — I'd write it down explicitly so it doesn't creep back in month three."

    Handling a challenge
    "That's a fair objection. It would matter most if X were true — is it? If so I'd switch to Y."

    Closing
    "The riskiest assumption is X, so I'd build the thin slice that proves it first. If it holds, the rest is breadth rather than risk."

    Close

    Requirements you can test, decisions you can defend, and a contract that catches the drift

    Architecture is the set of decisions that are expensive to reverse. The process exists to make sure each of them is made deliberately, written down with its alternative, and checkable against the thing that eventually gets built.

    Ask before you draw

    Seven buckets, and the zeroth question. Adjectives become numbers before any box goes on the board.

    Decide with alternatives

    Every choice carries what it was chosen against and what would reverse it. That is a decision; anything less is an assumption.

    Compress to a contract

    Fifteen falsifiable sentences that a diff can violate. Drift becomes a text check rather than a judgement call.

    Design the failures

    Every outbound call gets a timeout, a retry budget, a breaker and a terminal state. Degradation is designed, not improvised.

    Plan the risk first

    A thin vertical slice that proves the risky assumption, then breadth. Each milestone ends at a test gate written with it.

    Let the trace be the status

    Checkboxes, reviews, checkpoints, decisions, git. Anyone can reconstruct where the project is without a meeting.

    ◆ The whole deck in one sentence

    Vision Brief → RFC + DRP → Constraints → Architecture → Work Plan → reviews — with a decision log underneath and a number behind every claim.
